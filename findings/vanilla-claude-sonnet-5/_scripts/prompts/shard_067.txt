VERDICT RUBRIC:

  "flag", tier "A" (counted as a real finding) requires ALL of:
    1. the argument is genuinely caller-controlled per the tool's own schema;
    2. you actually read every hop from argument to sink, including helpers;
    3. there is no effective guard on that path — or if a guard exists, you
       can name a concrete bypass (a specific input that gets past it);
    4. if the sink sits in a dependency, you checked the installed library
       source and it does not stop this;
    5. the impact is a genuine security property (confidentiality, integrity,
       auth, availability via a targeted mechanism) — not mere robustness,
       a crash on malformed input, or generic DoS.

  "flag", tier "B" (potential — real mechanism, weaker case) when the
  mechanism is real but: the behaviour is plainly the tool's advertised
  purpose (e.g. a "run this shell command" tool actually running shell
  commands is not itself a finding — but no input validation at all on top
  of that might still be Tier B if it exceeds what a reasonable caller
  expects); or it needs credentials/config/state you cannot confirm is
  present; or a guard exists and a bypass is plausible but you can't fully
  prove it from static reading alone.

  "clear" — record why, using one of these `reason` values:
    no-sink            — argument never reaches anything sensitive
    guarded            — an effective guard exists (say what it is)
    remote-api-wrapper — tool just forwards to a remote API/service; the
                          "sink" is the caller's own account/resource
    constant-args      — no caller-controlled input reaches the sink
    read-only-query     — read-only, no path/command/injection surface
    generated          — tool is dynamically generated (OpenAPI/schema/YAML)
                          and you reviewed the generator + data instead of a
                          per-tool handler
    other              — explain in `why`

EXPLICIT ANTI-FALSE-POSITIVE RULES — do not flag these:
  - a tool that only stores or echoes a caller-supplied string with no sink
    that ever opens/executes/interprets it;
  - log-injection unless CR/LF or control bytes actually reach a *structured*
    log format or a log *file* whose parsing/integrity breaks — "the code
    calls print()/logger.info() on user input" alone is NOT a finding;
  - weak PRNG / weak hash usage that is not used for any security decision
    (auth token, crypto key, password hash, nonce);
  - binding to 0.0.0.0, missing MCP transport auth, or bare --stdio exposure —
    these are properties of the MCP protocol/deployment, not of a specific
    tool; do not file them as per-tool findings (you may note them once in
    your shard summary if striking, but do not put them in the JSONL as
    tool-level flags);
  - anything argued only from the tool's description/docstring without
    reading the implementing code;
  - a tool whose entire declared purpose is "fetch/read this URL the caller
    gives you" being flagged for SSRF with no additional twist (e.g. it also
    resolves the URL server-side to internal metadata endpoints, or bypasses
    an allow-list) — plain URL-fetch-what-you're-told is Tier B at most, and
    only when there's something beyond "it fetches a URL".
